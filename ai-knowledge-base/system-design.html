System design

Architecture of the NavVis mobile challenge app (Android, Kotlin, Jetpack Compose), as built.

The app is one Gradle module split into three packages: ui, domain and data, plus di for wiring. Each layer only calls the layer below it. The domain package is plain Kotlin with no Android or data-layer imports, so it can be tested with JUnit alone.

This page started as the plan written before any code. It was updated at the end to match the code; the differences are listed under "What changed since the first version".

NumberParserTurns a number into section, item and result flag, or rejects it (null, outside 0 to 255, item without a title).
ResultComputerRuns the computation on Dispatchers.Default. A fair Semaphore limits it to cores minus one at a time, the 2 s timeout starts only once a job has its turn, and results are cached by input.
SimulatedAlgorithmStands in for the real algorithm: returns input % 100 and sleeps 1 to 5 ms, with about 1 in 100 inputs taking up to 3 s.
SectionListBuilderGroups rows by section and sorts them: item, then no result, results from low to high, pending, errors, then stream order.
StreamRepositoryRequests chunks until it gets an empty array, retries with exponential backoff and jitter (RetryPolicy), and remembers each stream's position so a retry carries on where it stopped.
StreamApiMakes one HTTP call. Reads and closes the response on OkHttp's thread, and returns typed errors instead of throwing.
ChunkDecoderDecodes each array element on its own, so one bad value doesn't drop the whole chunk.
MockInterceptorAnswers both endpoints inside OkHttp in the mock build. Hands out the next chunk per request, and can fail requests on purpose before taking a chunk.
MockScenarioTypeThe ten mock scenarios, from normal data to messy values, server errors and 100,000 numbers.
AppContainerBuilds the shared objects. In the mock build each session gets a new mock server; the real build keeps one repository for the whole process.

How data moves

  1. The app opens on a START button and fetches nothing yet. Pressing it starts a session: the ViewModel gets a repository from AppContainer and collects numbers() and inputs() at the same time.
  2. Each chunk comes with the stream index of its first value. Numbers are parsed as they arrive; invalid ones are counted as skipped.
  3. When both a row that needs a result and its input have arrived, whichever came second starts the computation. Until it finishes, the row shows a spinner.
  4. When the inputs stream finishes, rows past its last index become "missing input".
  5. Every change bumps a counter in a StateFlow. The rebuild loop snapshots the rows on the main thread, groups and sorts them on Dispatchers.Default, publishes the new UiState, then waits 100 ms. Changes during the build or the wait are combined into the next rebuild.
  6. If a stream still fails after its retries, its status becomes failed: a full-screen error if no rows are showing, a banner if they are. Retry continues from the next index.
  7. Picking a scenario in the mock build cancels the session's scope, which stops its collectors and computations, and goes back to START. The next START begins a new session with empty rows.

Design decisions

  • One module with packages per layer. Splitting into Gradle modules would add build setup without much benefit at this size.
  • Manual dependency injection through a small AppContainer. Hilt would work, but it is a lot of setup for this many classes.
  • The mock sits inside OkHttp, so the mock build runs the real decoding and retry code. A mock and a real product flavor pick which one is installed.
  • The list is rebuilt on a timer, not on every event. With thousands of results finishing per second, rebuilding on each one would waste CPU and cause jank.
  • Each run of the streams is a session with its own coroutine scope, a child of viewModelScope. Cancelling it is how switching scenarios stops all old work at once.
  • The computation timeout starts after a job gets its turn. Otherwise, with 100,000 inputs, most jobs would time out while still waiting in line.
  • HTTP responses are read and closed on OkHttp's thread. Closing an unread HTTP/2 response writes to the network, which Android forbids on the main thread.
  • Release builds use R8, and a benchmark build type (release settings, debug key) is used to measure performance.

What changed since the first version

Things the first plan didn't have, all added while building and testing:

  • Sessions in the ViewModel and a mock server per session, for the scenario menu.
  • Ten mock scenarios, including ones that fail requests on purpose.
  • The error views (full screen and banner) as their own file.
  • A semaphore in ResultComputer so the timeout doesn't count queue time.
  • Reading and closing responses in OkHttp's callback, after a crash on the main thread.
  • items() per section instead of item() per row, after measuring jank with 100,000 rows.
  • SessionTimer and the benchmark build type, for performance numbers.
  • The NavVis theme, from brand_guidelines.html.
