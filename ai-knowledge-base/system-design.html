System design

Proposed architecture for the NavVis mobile challenge (Android, Kotlin, Jetpack Compose).

The app is one Gradle module split into three packages: ui, domain and data. Each layer only calls the layer below it. The domain package is plain Kotlin with no Android imports, so it can be tested with JUnit alone.

Components

ClassJob
StreamScreenDraws section headers and rows in a LazyColumn. Shows each stream's status, a count of skipped numbers, and a Retry button when a stream fails. Contains no logic.
StreamViewModelCollects both streams, stores rows by index, pairs number i with input i, asks for results, and exposes one StateFlow<UiState>.
NumberParserTurns a raw JSON value into section, item and result flag, or marks it invalid.
ResultComputerRuns the slow computation on Dispatchers.Default with a cap on parallel jobs, a timeout, and a cache keyed by input value.
SectionListBuilderGroups rows by section and sorts them by the rules in assumptions.md.
StreamRepositoryRequests chunks in a loop until it gets an empty array. Retries failed requests with exponential backoff and jitter. Exposes numbers() and inputs() as flows.
StreamApiMakes the HTTP call and decodes the array element by element, so one bad value doesn't drop the whole chunk.
MockInterceptorOkHttp interceptor that returns fake responses for a chosen scenario (truncation, nulls, server errors, a large dataset).

How data moves

  1. The ViewModel starts collecting numbers() and inputs() in parallel inside viewModelScope.
  2. Each chunk is appended to the row store at the next free index. Numbers are parsed as they arrive.
  3. If a row needs a result and its input has arrived, the ViewModel asks ResultComputer for it. Until then the row shows as pending.
  4. Every change marks the store as dirty. A single collector rebuilds the sorted list off the main thread at most once every 100 ms and publishes it as UiState.
  5. If a stream still fails after its retries, its status becomes failed. Retry picks up from the last index received.

Design decisions

  • One module with packages per layer. Splitting into Gradle modules would add build setup without much benefit at this size.
  • Manual dependency injection through a small AppContainer. Hilt would work, but it is a lot of setup for eight classes.
  • The mock sits inside OkHttp, so mock mode still runs the real decoding and retry code. A mock and a real product flavor pick which one is installed.
  • The list is rebuilt on a timer, not on every event. With hundreds of results finishing per second, rebuilding on each one would waste CPU and cause visible jank.
